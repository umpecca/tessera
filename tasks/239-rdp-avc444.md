# Task 239: Full color (AVC444) for RDP panes

Status: complete

Let an RDP pane show H.264 in 4:4:4 (AVC444) when the server sends it, as a
connection option, alongside the 4:2:0 picture Tessera shows today.

## Background

Task 237 decodes the server's H.264 with WebCodecs and draws it straight onto
the canvas. RDP's AVC444 (MS-RDPEGFX 2.2.4.5, 2.2.4.6) sends each picture as
two 4:2:0 views through one H.264 stream: a main view (luma plus subsampled
chroma, an ordinary picture) and an auxiliary view packing the chroma samples
the main view leaves out. Tessera's patched IronRDP already offers the EGFX
10.x capability sets, which imply AVC444, but it hands the auxiliary view to
the browser with no regions, and the browser decodes it only to keep the
stream in step and shows the main view: correct, but at 4:2:0.

Remotr has added AVC444 support (user report, 2026-10-28). Remotr has so far
sent AVC420 under EGFX 10.7; whether it now sends AVC444, and which layout
(AVC444 or AVC444v2), is not yet measured.

The client cannot ask for 4:2:0 under EGFX 10.x: in those sets AVC444 and
AVC420 stand or fall together (`AVC_DISABLED` turns off both), and the server
picks. FreeRDP's server reads the thin-client flag only for 8.x sets, and
Remotr sends no H.264 at all under 8.1 (task 237). So the option is about what
Tessera shows, not what the server sends.

IronRDP `master` already recombines AVC444 on the CPU (`ironrdp-egfx`
`avc444.rs`, `Yuv444Frame`), for decoders that return YUV planes. That is the
WebAssembly path task 237 found too slow on iPad, and it needs the planes back
from the browser decoder. The reference is used here for the mapping, not run.

## Decisions

- **Option:** a "Full color (4:4:4)" checkbox in the RDP sign-in dialog,
  shown when H.264 is available, off by default, remembered per browser in
  `localStorage` like the keep-session choice. Kept sessions resumed without
  the dialog use the remembered choice. Off, or with nothing to combine,
  everything is as today.
- **GPU combination:** with the option on, each decoded view is copied out of
  its `VideoFrame` as raw planes (`copyTo`, I420 or NV12), uploaded to WebGL2
  textures, and combined by shaders into a persistent 4:4:4 picture: one pass
  per view writes it within the view's regions (MS-RDPEGFX 3.3.8.3.2 and
  3.3.8.3.3), and one pass applies the reverse chroma filter and the
  MS-RDPEGFX color transform (3.3.8.3.1) into an offscreen WebGL canvas, whose
  painted regions are drawn onto the pane's canvas. Integer shader math
  matching `avc444.rs` so the output equals IronRDP's CPU reference.
- **Fallback:** no WebGL2, or a frame format other than I420 or NV12, falls
  back to showing the main view, as today. AVC420 pictures always take the
  direct path.
- **Toolbar label:** "H.264 4:4:4" once a combined picture is drawn, "H.264"
  otherwise, so the user sees what they get.
- **One decoder for both views**, as today: IronRDP treats them as one H.264
  stream. With Remotr every frame is an IDR, so this is safe either way.

## Phase 1: IronRDP

On the `tessera-h264` and `tessera-headless` branches:

1. `ironrdp-egfx`: `present` gains the view: AVC420, or an AVC444 main or
   auxiliary view with its layout (v1 or v2) and whether another view of the
   same picture follows. The auxiliary view keeps its own regions.
2. `ironrdp-web`: the `h264_frame_callback` receives
   `(data, regions, surfaceId, view)`.
3. `ironrdp-headless`: the H.264 event payload carries the view byte.

Re-export the series to `third_party/ironrdp/patches/`, rebuild
`web/vendor/rdp.js` and `internal/rdpsession/ironrdp_headless.wasm`, and
produce combination fixtures from `Yuv444Frame` (planes of both views for v1
and v2 with partial regions, and the expected RGBA) for Phase 2's tests.

Done 2026-10-28: commits 0006-0008 on `tessera-headless` (worktree
`IronRDP-headless`), on top of 0001-0005; `git am` of the exported series on
the base commit gives the branch's tree. The view is coded in one byte: 0
AVC420, 1 main, 2 auxiliary, +4 AVC444v2, +8 auxiliary follows. Checks:
`ironrdp-egfx` tests (67), the EGFX suite (292, the AVC444 presenting tests
rewritten for views and regions, plus a luma-only and a chroma-only case),

## Phase 2: Tessera

- `internal/rdpsession`: `ViewH264` carries the view byte; `web/rdp-viewer-wire.mjs`
  and `web/rdp-viewer.mjs` pass it on.
- `web/rdp-avc444.mjs`: the WebGL2 combiner, taking raw planes so it can be
  tested without a decoder.
- `web/rdp-h264.mjs`: with `fullColor`, route AVC444 views through the
  combiner (in decode order), defer painting a main view whose auxiliary view
  follows, and report 4:4:4 once drawn.
- `web/app.js`: the checkbox, the preference, the label.
- Tests: Node tests for routing with a fake decoder and combiner; a browser
  check of the shaders against the Phase 1 fixtures (headless Chrome).

Done 2026-10-28. With full color on, every picture goes through one promise
chain so AVC420 and combined pictures stay in order; the combiner (a WebGL2
context on an `OffscreenCanvas`) is created on the first AVC444 view. Shader
check: fixtures from IronRDP's `Yuv444Frame` (v1 and v2, 48x40 and 50x37,
a full update, then main and auxiliary views over different rectangles, then
a luma-only update), fed as I420 and NV12 with padded strides, to an
`OffscreenCanvas` and a document canvas, read back through a 2D canvas: all
16 match the reference byte for byte in headless Chrome (SwiftShader).
Mutating the V1 row mapping, the reverse-filter threshold, the V2 quarter
offset or the main view's chroma area each fails it. The fixtures and check
page were scratch files, not committed. 865 JS tests, `go test ./...` and the
IronRDP interop test pass.

Not checked without a device: the `VideoFrame` format iPad Safari's hardware
decoder gives (anything but I420 or NV12 falls back to 4:2:0, and the label
stays "H.264"), and the cost per frame.

## Phase 3: iPad check

From the iPad over HTTPS against Remotr: what Remotr sends (codec and layout),
that the picture is correct (colored text, gradients, odd-width windows),
frame rate and latency with the option on and off.

Results 2026-10-28 (iPad Safari, then MacBook Chrome, against Remotr on the
Tessera host; a test-only overlay and capture in a scratch copy of `web/`):

- Remotr sends AVC444v2, both views in each update, every frame an IDR,
  both views with the same SPS; WebCodecs returns NV12 on both browsers.
  Combining costs about 0.4 ms for `copyTo` and 2 ms for combine and paint.
- With the option on, the picture flickered, felt slow and the session
  dropped after 5 to 25 seconds. A probe build of the host module logging
  every EGFX PDU found the cause: in AVC444 mode Remotr decodes into an
  offscreen surface (65532, 1376 wide) and copies it to the output surface
  with `SurfaceToSurface` every frame, about 7 a second, even for a static
  screen. The compositor never had the presented H.264 pixels, so each copy
  painted the output black (in kept sessions as a 4 MB image per frame,
  which overflowed the host's viewer backlog and dropped the viewer with no
  reason shown). Not specific to full color: it also happens with the
  option off.
- Fix: patches 0009-0011 (surface-aware presenting, above), the presenter's
  per-surface canvases and in-order pipeline, and the host replaying where
  surfaces are shown to a new viewer. Afterwards: no flicker, no drop,
  "H.264 4:4:4" shown, and the only black images are the full-screen black
  `SolidFill` Remotr sends at the start of each session, before any video.
- The browser-only path (not kept on the host) also works against Remotr,
  checked separately by the user. The earlier runs were all kept sessions,
  since "Keep this session on the host" is remembered and on by default.
- The test setup (scratch server, capture receiver, probe builds) was
  removed afterwards.
