# Task 237: H.264 for RDP panes

Status: complete

Move the RDP pane from the patched IronRDP 0.7.0 bundle to a patched build of
IronRDP `master` that uses the Graphics Pipeline (MS-RDPEGFX) with H.264
decoded by the browser's hardware decoder (WebCodecs), drawn straight onto the
canvas.

## Background

Task 236 shipped IronRDP 0.7.0 with `third_party/ironrdp/putimagedata.patch`,
which fixed a softbuffer conversion that capped iPad Safari at about 3 Mpx/s.
That client has no EGFX, so servers fall back to legacy bitmap updates.

An experiment on IronRDP `master` (7fc80c4d), tested from an iPad against
Remotr on macOS, found:

- EGFX without H.264 is slower than the patched 0.7.0 on the iPad and drops
  frames: the non-H.264 EGFX codecs are decoded in WebAssembly, which is slow
  there.
- Remotr confirms EGFX 10.7 and sends the whole desktop as AVC420: Annex B,
  High profile level 3.2 (`avc1.640020`), every frame an IDR, an SPS about
  every 10 frames, about 8 KB per frame (roughly a tenth of the legacy path's
  bandwidth).
- WebCodecs on the iPad decodes 1080p at about 765 fps and, with
  `copyTo({ format: "RGBA" })`, delivers RGBA into WebAssembly memory at
  about 0.9 ms per frame. Reading frames back through a canvas manages only
  12 fps.
- Remotr's SPS has no VUI `max_num_reorder_frames`, so the decoder holds a full
  DPB (6 frames at 1216x640) before output: about 117 ms of latency. Rewriting
  each SPS to declare `max_num_reorder_frames = 0` cut it to 2.6 ms average,
  4 ms max, with nothing held back.
- Input-to-paint latency (from sending an input to the next screen update):
  0.7.0 averaged 19 ms; `master` + H.264 averaged 10 ms, and 7 ms (19 ms max)
  with the server pointer off. That last configuration also felt smoothest.
- `master` turned `enable_server_pointer` on by default (3f0ab8d1). Remotr
  sent no pointer bitmaps either way, and 0.7.0 had it off, so Tessera loses
  nothing by turning it off.
- `master` already includes the softbuffer fix (#1374), so
  `putimagedata.patch` is not needed on it.
- Remotr needs EGFX 10.x for H.264: offered only 8.1 with AVC420, it confirms
  8.1 and sends uncompressed bitmaps.
- In a few minutes of normal use (app switching, scrolling, menus, windows,
  typing), Remotr sent one solid fill and nothing else besides AVC420: no
  surface-to-surface copies, no cache operations, no other codecs, and one
  surface mapped at 0,0. Those are the operations the fast path doesn't handle,
  so it is safe with Remotr.

## Decisions

- **Source:** the IronRDP checkout at `/Volumes/Data/projects/IronRDP` (later a
  fork of it). Its experiment branch, `tessera-egfx` in the
  `/Volumes/Data/projects/IronRDP-egfx` worktree, gets cleaned into the commits
  below.
- **Vendored, prebuilt:** Tessera commits the built bundle as
  `web/vendor/rdp.js`, as now. `npm run build:web` does not touch it, and
  neither CI nor a Tessera build needs Rust or the npm registry for it.
- **Standalone:** nothing is fetched at runtime and there is no CDN. The H.264
  decoder is the browser's own, so Tessera ships no codec, and no OpenH264 or
  H.264 licensing applies. Tessera stays one Go binary.
- **Fast path:** decoded frames are drawn straight to the canvas (GPU) instead
  of through IronRDP's compositor. The compositor-integrated path (async
  decoding inside `ironrdp-egfx`, RGBA through WebAssembly) is future work,
  needed only if a server mixes H.264 with cache or surface-to-surface
  operations over video regions.
- **EGFX only with H.264:** when H.264 isn't available, connect exactly as today
  (no EGFX), since EGFX without H.264 is slower on the iPad.

## Phase 1: IronRDP branch

Rebuild the experiment as a short series on a branch based on a pinned `master`
commit, without the diagnostics.

1. `ironrdp-egfx`: `H264Decoder::presents_frames()` and
   `present(surface_id, data, regions)`; `decode_avc420` hands the frame to such
   a decoder and skips the compositor. Keep this commit self-contained with
   tests, since it is the part to propose upstream.
2. `ironrdp-web`: an `enable_egfx` extension that sets
   `support_dyn_vc_gfx_protocol` and registers `GraphicsPipelineClient`; an
   `h264_frame_callback` extension whose decoder sends each frame (Annex B data
   plus `[x, y, width, height]` regions) over a channel drained in the session
   loop into the JavaScript callback; `Canvas::fit()` so a `ResetGraphics`
   resizes the canvas.
3. `web-client/iron-remote-desktop-rdp`: `enableEgfx()` and
   `h264FrameCallback()` helpers.
4. Drop the experiment-only code: `H264Probe`, the "EGFX confirmed" and codec
   logs, the `h264_probe` extension.
5. AVC444. The decoder must claim YUV output so the EGFX 10.x capability sets
   (which pair AVC420 with AVC444) are offered: offered only V8.1 with AVC420,
   Remotr confirms V8.1 and sends uncompressed bitmaps, no H.264. Remotr has
   never sent AVC444, so handle it as a fallback: present an AVC444 frame's
   main view (an ordinary 4:2:0 picture) through the same JavaScript decoder
   path as AVC420, and drop the auxiliary chroma stream and chroma-only
   updates. The picture stays correct at 4:2:0 chroma. Replace the prototype's
   gray frames; never ship a path that can draw gray.

Record the base commit, the patch series (`git format-patch`) and the exact
build commands in `third_party/ironrdp/`. Keep `putimagedata.patch` until
Phase 4 replaces the 0.7.0 bundle it belongs to.

Done 2026-10-27: branch `tessera-h264` at 7fc80c4d, three commits, exported to
`third_party/ironrdp/patches/` (`git am` on the base commit reproduces the

## Phase 2: Tessera integration

- `web/rdp-h264.mjs`: the presenter. It keeps one `VideoDecoder`, configured
  from each stream's SPS (`avc1.PPCCLL`) with `optimizeForLatency` and
  `prefer-hardware`; rewrites each SPS before decoding; marks IDR access units
  as key chunks; maps output frames back to their regions by timestamp and
  `drawImage`s each region; on a decoder error, drops frames until the next IDR
  and recreates the decoder; closes on disconnect.
- `web/rdp-h264-sps.mjs`: the SPS rewrite (from the experiment's
  `h264-sps.mjs`): RBSP unescaping, SPS and VUI parsing, and adding or replacing
  `bitstream_restriction` with `max_num_reorder_frames = 0`.
- `web/app.js`, before `connect()`: always
  `builder.extension(module.enableServerPointer(false))`. Offer H.264 only when
  `window.isSecureContext`, `VideoDecoder` exists and
  `VideoDecoder.isConfigSupported({ codec: "avc1.640020" })` resolves
  supported; then add `enableEgfx(true)` and `h264FrameCallback(...)`.
  Otherwise connect as today.
- `web/embed.go`: embed the two new modules.
- The pane says when it is using H.264, for example in the toolbar's status, so
  a fallback is visible. When an iPad opens Tessera over HTTP, the existing iPad
  HTTP guidance should mention that hardware video needs HTTPS.

Done 2026-10-27. Until Phase 4 swapped the bundle, `app.js` checked the

## Risks and open questions

- `master` is unreleased and moving. Pin a commit and re-test before each
  rebase, including input-to-paint latency.
- The fast path assumes every surface is mapped at the canvas origin and that
  video regions are never read back by cache or surface-to-surface operations.
  True for Remotr; another server may break either. Log when either assumption
  breaks, and fall back where possible.
- Anything IronRDP's compositor redraws over a video region paints its stale
  pixels there, for example a full-surface update after `ResetGraphics`.
  Remotr sends every frame as an IDR, so the next frame repairs it within a
  frame, but check this on resize in Phase 3.
- AVC444 is handled by its main view only (Phase 1, step 5) and has not been
  seen from a real server.
- Turning the server pointer off gives every server the browser's arrow, as
  0.7.0 does today. Servers that send pointer shapes (Windows) could get them
  back later through a per-server setting.
- Only iPad Safari and Remotr have been tested so far.
- Upstream may prefer a different decoder hook. Keep step 1 small so it is easy
  to revise or drop once IronRDP's web client gains EGFX itself (#1464, #790).
